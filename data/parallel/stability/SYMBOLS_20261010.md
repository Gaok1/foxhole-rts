## Partial names without a PDB

The installed llvm-readobj provides 4353 exports and the RuntimeFunction ranges of .pdata.
For each RVA in the stack, I looked for the range containing the address and accepted a
name ONLY when an export starts exactly at the beginning of that range.
Do not assign a name from the nearest preceding export: that heuristic gave
wrong names for separate private functions. Data in crash_ranges_20261010.json.

- 0x2c6b92 and 0x2c6d99 belong to the range [0x2c6120, 0x2c6f3a), whose start
  exports RC::LuaType::push_structproperty(PusherParams const&).
- 0xb99c75 belongs to [0xb99c00, 0xb99d65): RC::LuaMadeSimple::Lua::call_function(int,int) const.
- 0xb9d34c belongs to [0xb9cf40, 0xb9d373): RC::LuaMadeSimple::process_lua_function(lua_State*).
- The other RVAs still have no proven name; do not call 0xc77cab an ASM function
  just because an ASM export precedes that address.

The names above locate frames, they do NOT attribute the cause. push_structproperty
points to a struct conversion path in the stacks that contain these RVAs, but it does not
identify which UProperty/UFunction/actor nor the instruction that made the invalid access.
The Registry error was not linked to these frames either. Next RE step: the UE4SS

## Public source of the exact commit checked

GitHub Tree resolved 5418fa4e to 5418fa4ed9f1e8379d28ee7bbc3235c7e0c71b09,
without truncation. Only three public source files were downloaded to
D:/tools/ue4ss-source-5418fa4e (they are not decompilation of the game):
LuaUObject.cpp, LuaXStructProperty.cpp and LuaMadeSimple.cpp.

- Registry::get_function_ref does rawgeti on the registry and checks the FUNCTION type;
  if it is not a function, it discards the value and enters error handling. The message
  does not identify which registration/callback originated the call.
- handle_error generates a traceback, notifies the error callbacks and clears the Lua stack;
  throw_error picks a C++ exception or luaL_error depending on whether errorJmp is available.
  This logic deserves attention in the reproduction, but it does not show corruption happened.
- process_lua_function is the trampoline of the C++ functions exposed to Lua. Its frame
  does NOT prove a keybind: any function registered on that bridge can go through it.
- push_structproperty supports reading, conversion to a table, writing and parameters;
  the name alone does not separate these operations. In the compatible PE, 0x2c6b92 is right
  after a call on the branch that recognizes a table and before discard_value: the flow
  matches converting a Lua table into a struct in the source. This locates a
  write path in the stack containing that address, not the guilty property.
- 0x2c6d99 is after another internal call, without an exact exported name; do not
  classify that call by the approximate name objdump prints for the address.

There is no reproduction of an invalid func_id/registry_index nor the struct's name in the
dumps analyzed. No patch to the loader/mod was justified by this isolated reading.
